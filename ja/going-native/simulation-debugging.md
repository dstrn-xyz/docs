<a name="はじめに"></a>

## はじめに

ネイティブシミュレーション環境は開発中の迅速なイテレーションを提供します。本番ビルドとは異なりシミュレーターはローカル開発サーバーに直接接続しホットリロードをサポートします。

<a name="シミュレーションモード"></a>

## シミュレーションモード

シミュレーションモードは開発サーバーのurlをネイティブランタイムに自動的に注入します。サーバーがまだ実行されていない場合フレームワークはサーバーを起動します。

<a name="iosシミュレーション"></a>

### iosシミュレーション

```bash
dstrn simulate --ios
```

フレームワークはシステム上で利用可能なiosシミュレーターを検索します。既に起動しているデバイスを優先し最新の利用可能なiphoneモデルにフォールバックします。

要件:
- コマンドラインツールがアクティブに設定された完全なxcodeアプリケーション
- xcodeで設定された1つ以上のiosシミュレーター

シミュレーターはswiftランタイムとjavascriptアプリケーションの両方からのコンソール出力を表示します。`r`キーを押してwebviewをリロードします。`q`キーを押して終了します。

<a name="androidシミュレーション"></a>

### androidシミュレーション

```bash
dstrn simulate --android
```

フレームワークは最初に接続されている実機デバイスを確認します。見つからない場合は設定されているandroid仮想デバイスを検索し最初のデバイスを自動的に起動します。

要件:
- インストール済みのandroid sdk
- 利用可能なプラットフォームツール（adb）
- java開発キット（jdk 17からjdk 21、またはandroid studioバンドルjbr）
- android studioで設定された1つ以上のavd

エミュレーターの起動には最大1分かかる場合があります。フレームワークはアプリケーションをインストールして起動する前にデバイスの準備が整うのを待ちます。

> [!NOTE]
> androidエミュレーターは`localhost`を`10.0.2.2`にマッピングします。開発サーバーはエミュレーター内からこのホストアドレスでアクセスできる必要があります。

<a name="desktopシミュレーション"></a>

### desktopシミュレーション

```bash
dstrn simulate --desktop
```

デスクトップランタイムはtauri webviewを搭載したネイティブウィンドウを開きます。これはブラウザと同様に動作しますがブリッジを介してネイティブシステムapiにアクセスできます。

要件:
- インストール済みのrustツールチェーン
- 利用可能なtauri cli

デスクトップシミュレーションは最も高速なイテレーションサイクルです。ウィンドウはリサイズ可能で標準のキーボードショートカットに応答します。コンソールにはrustランタイムとjavascript環境の両方からの出力が表示されます。

<a name="シミュレーションと本番環境の比較"></a>

## シミュレーションと本番環境の比較

シミュレーションモードと本番環境にはいくつかの重要な違いがあります:

| 項目 | シミュレーション | 本番環境 |
| ---------- | ---------------------- | -------------------- |
| urlソース | 環境変数 | 設定されたurl |
| サーバー | ローカル開発 | リモートまたは静的 |
| リロード | `r`キーで即座に実行 | アプリの完全再起動 |
| デバッグ | コンソール出力有効 | 最小限のログ |
| ネットワーク | localhost/10.0.2.2 | 本番エンドポイント |

最も重要な違いはurlの解決です。シミュレーターは`DSTRN_DEV_URL`環境変数を介して開発サーバーのurlを受け取ります。本番ビルドは[`config/native.js`](getting-started.md#url設定)で設定されたurlを使用するかアプリケーション設定にフォールバックします。

本番ビルドでホワイトスクリーンが表示される場合は設定されたurlにアクセス可能であり有効なhtmlが返されていることを確認してください。トラブルシューティング手順については[一般的な問題](#起動時のホワイトスクリーン)を参照してください。

<a name="デバッグ"></a>

## デバッグ

フレームワークにはリアルタイムのパフォーマンス監視、ネットワークインスペクション、コンソールログ、およびdom分析を提供する統合デバッグバーが含まれています。デバッグバーはローカル開発時に自動的にアクティブ化されボトムバーインターフェースを介して切り替えることができます。

主要機能:
- サーバータイミングとクエリプロファイリング
- メモリリーク検出とcpu監視
- 完全なヘッダーとペイロードを備えたネットワークリクエストインスペクション
- スタックトレース付きのコンソールログ集約
- 視覚化機能を備えたライブdomインスペクター
- ソケットイベント監視
- コンポーネント状態追跡

デバッグバーはネイティブwebviewと統合されておりios、android、desktopプラットフォーム全体で同じエクスペリエンスを提供します。

<a name="iosデバッグ"></a>

### iosデバッグ

ios webviewのデバッグはsafari開発者ツールを通じて行われます:

1. safariの環境設定で開発メニューを有効にする
2. シミュレーターでアプリを起動する
3. safariの開発メニューを開く
4. シミュレータ > 対象アプリ > wkwebviewを選択する

これでjavascriptコンソール、ネットワークインスペクター、domビューアーにフルアクセスできるようになります。ブレークポイントとステップ実行デバッグは期待どおりに機能します。

swiftからのランタイムログはxcodeコンソールまたはシミュレーションコマンドを実行したターミナル出力に表示されます。

<a name="androidデバッグ"></a>

### androidデバッグ

android webviewのデバッグにはchrome devtoolsを使用します:

1. エミュレーターまたは実機デバイスでアプリを起動する
2. chromeを開いて`chrome://inspect`に移動する
3. リモートターゲットリストで対象アプリを見つける
4. inspectをクリックしてdevtoolsを開く

webviewデバッグはデバッグビルドで自動的に有効化されます。フレームワークはlocalhostをエミュレーターのホストipにマッピングするネットワークアダプターを注入します。

ネイティブランタイムログを表示するには`adb logcat`を使用します:

```bash
adb logcat -s dstrn:V
```

<a name="desktopデバッグ"></a>

### desktopデバッグ

デスクトップアプリケーションはtauri webviewを通じてdevtoolsをサポートします。ウィンドウ内の任意の場所を右クリックして要素を調査を選択します。

コンソール出力はdevtoolsコンソールとシミュレーションを起動したターミナルの両方に表示されます。rustのログには`[dstrn]`プレフィックスが付きます。

<a name="一般的な問題"></a>

## 一般的な問題

<a name="起動時のホワイトスクリーン"></a>

### 起動時のホワイトスクリーン

症状: アプリは起動するがコンテンツのない白い画面のみが表示される。

**シミュレーションモードの場合:**

開発サーバーが実行されておりアクセス可能であることを確認します:

```bash
curl http://localhost:8250
```

androidの場合はエミュレーターのマッピングをテストします:

```bash
adb shell curl http://10.0.2.2:8250
```

curlが成功してもアプリが白画面を表示する場合はブラウザコンソールでjavascriptエラーを確認してください。

**本番ビルドの場合:**

最も一般的な原因はアクセス不能または設定ミスのあるurlです。本番ビルドは開発urlを自動的には受け取りません。

ネイティブ設定を確認してください:

```javascript
// config/native.js
export default {
  index: 'https://your-actual-domain.com',
};
```

`index`がnullの場合は[`Config('app.url')`](../getting-started/configuration.md#app-config)および[`Config('app.port')`](../getting-started/configuration.md#app-config)が本番サーバーを指していることを確認してください。

サーバーがネットワーク接続を必要とする場合はアプリがオフラインでも動作できるように[静的フォールバック](getting-started.md#静的フォールバック)の実装を検討してください。

<a name="ネットワークリクエストの失敗"></a>

### ネットワークリクエストの失敗

**iosにおけるcorsエラー:**

iosではオリジン間リクエストに対して明示的なcorsヘッダーが必要です。apiがフロントエンドと異なるドメインで実行されている場合はサーバーに適切なcorsヘッダーが含まれていることを確認してください。

**androidにおける接続拒否:**

androidはデフォルトで平文httpをブロックします。開発サーバーまたは本番サーバーがhttpsではなくhttpを使用している場合はマニフェストで平文トラフィックを有効にする必要があります。

フレームワークはデバッグビルドではデフォルトで平文を許可します。本番ビルドでは明示的に設定されていない限りhttpsが強制されます。

**localhostにアクセスできない:**

androidではlocalhostは開発マシンではなくエミュレーター自体を指します。すべてのlocalhost参照はネットワークポリフィルによって自動的に`10.0.2.2`に書き換えられます。

iosおよびdesktopではlocalhostは期待どおりに動作します。

<a name="静的アセットが読み込まれない"></a>

### 静的アセットが読み込まれない

cssまたはjavascriptファイルが404エラーを返す場合はパスがサーバー設定と一致していることを確認してください。

ネイティブwebviewはページurlに対して相対urlを解決します。ページが`https://api.example.com/`からロードされアセットが`https://cdn.example.com/`から配信されている場合はhtmlで絶対urlを使用してください。

静的フォールバックサイトはバンドルルートに対してアセットを解決します。`/css/dstrn.css`のようなパスはリモートモードとローカルモードの両方で正しく動作します。

<a name="javascriptエラー"></a>

### javascriptエラー

エラーメッセージとスタックトレースについてはjavascriptコンソールを確認してください。フレームワークのエラーハンドラーはローカルモードで詳細なデバッグ情報を表示します。

一般的な原因:
- ポリフィルの欠落による未定義変数
- ネットワークリクエストをブロックするcors問題
- dom要素が準備できる前にアクセスされるタイミング問題

ネイティブブリッジはすべてのプラットフォームで`App.native`（または`window.App.native`）として利用可能です。コードがネイティブ機能に依存している場合はメソッドを呼び出す前にブリッジが存在することを確認してください。

<a name="ログ出力"></a>

## ログ出力

ネイティブランタイムは標準化されたログメッセージを出力します:

```
[dstrn] loading remote: https://api.example.com
[dstrn] webview ready
[dstrn] load failed: network error
[dstrn] attempting fallback
```

シミュレーションモードは本番環境よりも詳細に出力されます。本番環境では重大なエラーと状態変更のみがログに記録されます。

プラットフォームごとにネイティブログをフィルタリングできます:

```bash
# ios
xcrun simctl spawn booted log stream --predicate 'process == "dframework"'

# android
adb logcat -s dstrn:V

# desktop
# logs appear in terminal where simulate was run
```
